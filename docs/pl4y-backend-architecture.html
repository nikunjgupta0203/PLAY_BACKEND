§ 01

System shape

One deployable API process, one worker process running the same image, and a small set of managed dependencies. Nothing here is a microservice, and nothing here needs to be.

The product loop in the brief — discover → play → compete → track → rank — is a single transactional story per player. Splitting it across services buys distributed transactions and buys nothing else at this scale. So: a modular monolith. Hard internal boundaries between thirteen modules, one process, one database. The boundaries are what make a later split cheap; the split itself waits until something forces it.

Two processes from one image. The worker exists because seat-hold expiry, rating periods and score fan-out must not compete with request latency — not because the domain is distributed.

The decisions that shape everything downstream

API style
GraphQL, one endpoint

The Home screen alone needs six unrelated collections. One typed round trip beats six REST calls on Indian mobile networks. The cost: depth and complexity limits are mandatory from day one, not later.

Schema construction
Pothos, code-first

Without NestJS decorators, Pothos gives the strongest TypeScript inference available. Its Prisma plugin resolves relations without hand-written loaders for the common cases.

Realtime
Pusher, not subscriptions

No WebSocket server to run, scale, or drain on deploy. The tradeoff: Pusher becomes a cache-invalidation transport and never a source of truth — see §09.

Money
The webhook is the truth

Razorpay’s client-side callback is a UI hint. A registration confirms only on a signature-verified payment.captured webhook, or on reconciliation against the Orders API.

Rating
Glicko‑2, versioned

Amateur players compete in bursts around tournaments. Glicko‑2’s rating deviation models that inactivity; Elo cannot. Stored append-only with an algorithm version on every row.

Sport-agnosticism
sport_id is NOT NULL

Every event, match, rating and ranking row carries it. Pickleball is a row in sports, never a branch in code. Formats and scoring rules are data, not enums.

Hosting assumption

The brief specified Razorpay and Pusher but not a host. This document assumes containers on a managed platform — Railway or Render through Sprint 6, AWS ECS Fargate at launch — with managed Postgres on Neon, managed Redis and Cloudinary for media. Nothing above the managed-data line changes if you decide otherwise; only §11’s deployment notes do.

§ 02

Runtime & composition

Express hosts four things: the GraphQL endpoint, the Razorpay webhook, the Pusher channel authorizer, and health checks. That list is closed — new features arrive as GraphQL fields, never as new routes.

LayerChoiceWhy this one

Middleware order is load-bearing

Razorpay signs the exact bytes it transmitted. If any JSON parser touches the webhook request first, the signature will never verify — and the failure presents as a credentials problem, which is how teams lose a day to it. Mount the webhook before the parser.

src/app.tscomposition root
// Order matters. Read the comments before reordering anything.
const app = express();
app.set('trust proxy', 1);                // behind the platform load balancer
app.use(helmet());
app.use(pinoHttp({ genReqId: () => randomUUID() }));

// Razorpay signs the RAW request body. This route must be mounted
// before express.json(), or HMAC verification fails silently forever.
app.post('/webhooks/razorpay',
  express.raw({ type: 'application/json' }),
  razorpayWebhook);

app.use(express.json({ limit: '256kb' }));

// Pusher hands the client a socket_id; we decide what it may subscribe to.
app.post('/pusher/auth', requireAuth, pusherChannelAuth);

app.get('/healthz', () => ok());          // process is alive
app.get('/readyz',  readiness);           // pg + redis reachable

await apollo.start();
app.use('/graphql',
  cors(corsPolicy),
  expressMiddleware(apollo, { context: buildContext }));

app.use(errorMiddleware);                 // last, always

Module contract

Every module is a directory with the same four parts and three rules — enforced by an eslint no-restricted-imports rule, not by code review:

  1. Resolvers never touch Prisma. They call a service and shape the result.
  2. Services never import GraphQL types. They take and return plain domain objects, which is what makes them callable from workers and webhooks too.
  3. Cross-module calls go through the other module’s index.ts, never its repository. registration may ask payments to create an order; it may not read the payments tables.
src/layout
src/
  app.ts                    // composition root, above
  worker.ts                 // same image, BullMQ entrypoint
  platform/                 // no domain logic lives here
    config.ts               // zod-parsed env; process exits at boot if invalid
    db.ts   redis.ts   queue.ts   outbox.ts
    pusher.ts   razorpay.ts   email.ts   cloudinary.ts
    auth/   errors/   logging/   loaders/
  modules/
    registration/
      schema/               // Pothos object types, inputs, resolvers
      service/              // business rules — the part worth testing
      repo/                 // Prisma queries and raw SQL
      events.ts             // domain events this module emits
      index.ts              // the ONLY surface other modules may import
    ...twelve more
  schema.ts                 // merges module schemas into one executable schema
Outbox, not an in-process event bus

Modules talk to each other synchronously through service calls. Side effects that can fail independently — sending a push, recomputing a ranking, publishing to Pusher — are written to an outbox table inside the same transaction as the state change, then drained into BullMQ by the worker. An in-process emitter looks decoupled and quietly loses work whenever the process dies mid-request.

§ 04

Data model

PostgreSQL 16, one schema, migrations through Prisma. The tables below are the ones with non-obvious shape; the rest follow directly from the entity list in the brief.

Conventions

ConventionRuleReason
Primary keysUUIDv7Time-sortable, so index locality stays good without exposing a sequential count of your registrations to competitors.
Moneybigint *_paiseInteger minor units. No float touches money anywhere in the system, including in GraphQL.
Timetimestamptz, UTCEvents also store timezone so “Saturday 9am” survives a DST-free but multi-zone future.
Sportsport_id NOT NULLOn every competitive row. This is the single constraint that keeps multi-sport real rather than aspirational.
Status columnstext + CHECKPostgres enums need a migration to extend; a CHECK constraint does not, and states will change.
Deletionsoft only where auditedRegistrations, payments and matches are never hard-deleted. Games and follows are.

Events, categories, capacity

An event is the thing a player discovers; an event category is what they actually register for — Men’s Doubles 3.5, Mixed Doubles Open. Capacity, fee and format live on the category, never the event, because a single tournament sells eight different draws at eight different prices.

002_events.sqlddl
CREATE TABLE events (
  id              uuid PRIMARY KEY,
  sport_id        uuid NOT NULL REFERENCES sports(id),
  organizer_id    uuid NOT NULL REFERENCES users(id),
  venue_id        uuid REFERENCES venues(id),
  slug            text UNIQUE NOT NULL,        -- deep links: pl4y.app/e/{slug}
  title           text NOT NULL,
  description     text,
  city            text NOT NULL,
  geo             geography(Point,4326),       -- PostGIS; map + radius search
  timezone        text NOT NULL DEFAULT 'Asia/Kolkata',
  starts_at       timestamptz NOT NULL,
  ends_at         timestamptz NOT NULL,
  registration_closes_at timestamptz NOT NULL,
  cancellation_cutoff_at timestamptz,          -- full refund before this
  status          text NOT NULL DEFAULT 'draft'
                  CHECK (status IN ('draft','published','live','completed','cancelled')),
  cover_public_id text,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);

-- The Explore query. Partial index: unpublished events are never listed,
-- so they should not be in the index either.
CREATE INDEX events_discovery_idx
  ON events (sport_id, city, starts_at)
  WHERE status IN ('published','live');
CREATE INDEX events_geo_idx ON events USING gist (geo)
  WHERE status IN ('published','live');

CREATE TABLE event_categories (
  id              uuid PRIMARY KEY,
  event_id        uuid NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  sport_id        uuid NOT NULL REFERENCES sports(id),
  name            text NOT NULL,               -- "Men's Doubles 3.5"
  format          text NOT NULL,               -- singles | doubles | mixed_doubles | team
  team_size       smallint NOT NULL DEFAULT 1,
  draw_type       text NOT NULL DEFAULT 'single_elim_with_plate',
  skill_min       numeric(4,2), skill_max numeric(4,2),
  age_min         smallint,     age_max   smallint,
  capacity        integer NOT NULL,            -- entries, not people
  entry_fee_paise bigint NOT NULL,
  platform_fee_paise bigint NOT NULL DEFAULT 0,
  tax_bps         integer NOT NULL DEFAULT 1800,  -- 18% GST, basis points
  status          text NOT NULL DEFAULT 'open'
                  CHECK (status IN ('open','full','closed','drawn','completed'))
);
Price breakdown lives on the server

The brief requires the fee breakdown be shown before payment. The client never computes it. A priceQuote field on the category returns { entryFee, platformFee, tax, total } from the same function the order-creation path calls, so what the player agreed to and what Razorpay charges cannot drift.

Registration, teams and holds

Three tables carry the hard part of §07: registrations (one row per entry, singles or doubles), teams plus team_members, and seat_holds, which is what stops a category from overselling while four people sit in Razorpay’s checkout at once.

003_registration.sqlddl
CREATE TABLE registrations (
  id              uuid PRIMARY KEY,
  event_id        uuid NOT NULL REFERENCES events(id),
  event_category_id uuid NOT NULL REFERENCES event_categories(id),
  sport_id        uuid NOT NULL REFERENCES sports(id),
  captain_user_id uuid NOT NULL REFERENCES users(id),   -- the payer
  team_id         uuid REFERENCES teams(id),            -- null for singles
  status          text NOT NULL DEFAULT 'draft' CHECK (status IN (
                    'draft','awaiting_partner','payment_pending',
                    'confirmed','checked_in','withdrawn',
                    'expired','payment_failed','refunded')),
  seed            integer,                              -- set at draw time
  amount_paise    bigint NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now(),
  confirmed_at    timestamptz
);

-- A player cannot hold two live entries in the same category.
CREATE UNIQUE INDEX reg_one_live_per_player
  ON registrations (event_category_id, captain_user_id)
  WHERE status IN ('awaiting_partner','payment_pending','confirmed','checked_in');

CREATE TABLE registration_invites (
  id              uuid PRIMARY KEY,
  registration_id uuid NOT NULL REFERENCES registrations(id) ON DELETE CASCADE,
  invited_email   citext NOT NULL,        -- partner may have no account yet
  invited_user_id uuid REFERENCES users(id),
  token           text NOT NULL UNIQUE,   -- deep link payload
  status          text NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending','accepted','declined','expired')),
  expires_at      timestamptz NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now()
);

-- Capacity reservation with a TTL. Correctness lives in Postgres,
-- not Redis: a lost Redis key here means an oversold tournament.
CREATE TABLE seat_holds (
  id              uuid PRIMARY KEY,
  event_category_id uuid NOT NULL REFERENCES event_categories(id),
  registration_id uuid NOT NULL REFERENCES registrations(id) ON DELETE CASCADE,
  seats           smallint NOT NULL DEFAULT 1,
  expires_at      timestamptz NOT NULL,
  released_at     timestamptz
);
CREATE INDEX seat_holds_active_idx
  ON seat_holds (event_category_id)
  WHERE released_at IS NULL;

Matches, results and the append-only score log

005_tournament.sqlddl
CREATE TABLE matches (
  id              uuid PRIMARY KEY,
  tournament_id   uuid NOT NULL REFERENCES tournaments(id),
  event_category_id uuid NOT NULL REFERENCES event_categories(id),
  sport_id        uuid NOT NULL REFERENCES sports(id),
  bracket         text NOT NULL CHECK (bracket IN ('championship','plate')),
  round           smallint NOT NULL,        -- 1 = first round
  slot            smallint NOT NULL,        -- position within the round
  side_a_registration_id uuid REFERENCES registrations(id),
  side_b_registration_id uuid REFERENCES registrations(id),
  -- Wiring generated at draw time. Both directions, so a result
  -- advances the winner AND drops the loser into the plate in one write.
  winner_match_id uuid REFERENCES matches(id),
  winner_slot     smallint CHECK (winner_slot IN (0,1)),
  loser_match_id  uuid REFERENCES matches(id),
  loser_slot      smallint CHECK (loser_slot IN (0,1)),
  court_id        uuid REFERENCES venue_courts(id),
  scheduled_at    timestamptz,
  status          text NOT NULL DEFAULT 'scheduled' CHECK (status IN
                    ('scheduled','ready','live','awaiting_confirm','completed','walkover','void')),
  current_score   jsonb,                    -- denormalized; see §09
  score_seq       integer NOT NULL DEFAULT 0,
  UNIQUE (tournament_id, bracket, round, slot)
);
CREATE INDEX matches_live_idx ON matches (event_category_id, status, scheduled_at);

-- Append-only. Never updated, never deleted. This is what makes an
-- undo, a dispute, and a mid-match device failure all recoverable.
CREATE TABLE match_score_events (
  id              bigserial PRIMARY KEY,
  match_id        uuid NOT NULL REFERENCES matches(id),
  seq             integer NOT NULL,
  kind            text NOT NULL CHECK (kind IN
                    ('point','undo','timeout','game_end','match_end','correction')),
  scoring_side    text CHECK (scoring_side IN ('a','b')),
  state_after     jsonb NOT NULL,           -- full score, not a delta
  recorded_by     uuid NOT NULL REFERENCES users(id),
  recorded_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (match_id, seq)
);

CREATE TABLE match_results (
  match_id        uuid PRIMARY KEY REFERENCES matches(id),
  winner_registration_id uuid NOT NULL REFERENCES registrations(id),
  loser_registration_id  uuid REFERENCES registrations(id),
  games           jsonb NOT NULL,           -- [{a:11,b:7},{a:9,b:11},{a:11,b:5}]
  outcome         text NOT NULL CHECK (outcome IN ('played','walkover','retired','forfeit')),
  submitted_by    uuid NOT NULL REFERENCES users(id),
  confirmed_by    uuid REFERENCES users(id),
  confirmed_at    timestamptz,
  rating_applied  boolean NOT NULL DEFAULT false
);

Rating and rankings

Per the brief’s own design note: rating_events is the append-only log and rankings is a cache recomputed on write. The addition here is algo_version — it is what lets you replace Glicko‑2 later and recompute every historical rating without a schema migration.

006_rating.sqlddl
CREATE TABLE rating_events (
  id              bigserial PRIMARY KEY,
  player_id       uuid NOT NULL REFERENCES player_profiles(id),
  sport_id        uuid NOT NULL REFERENCES sports(id),
  match_id        uuid REFERENCES matches(id),
  rating_period_id uuid REFERENCES rating_periods(id),
  algo_version    text NOT NULL,            -- 'glicko2-v1'
  rating_before   numeric(7,2) NOT NULL,
  rating_after    numeric(7,2) NOT NULL,
  rd_before       numeric(7,2) NOT NULL,
  rd_after        numeric(7,2) NOT NULL,
  volatility_after numeric(7,5) NOT NULL,
  is_provisional  boolean NOT NULL DEFAULT false,
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON rating_events (player_id, sport_id, created_at DESC);
-- One settled rating row per player per match. Provisional rows are
-- superseded when the weekly period runs.
CREATE UNIQUE INDEX rating_events_settled_uniq
  ON rating_events (player_id, match_id) WHERE is_provisional = false;

CREATE TABLE rankings (
  sport_id        uuid NOT NULL REFERENCES sports(id),
  scope           text NOT NULL,            -- 'national' | 'city:Bengaluru' | 'age:35+'
  player_id       uuid NOT NULL REFERENCES player_profiles(id),
  rank            integer NOT NULL,         -- dense
  rating          numeric(7,2) NOT NULL,
  matches_played  integer NOT NULL,
  movement        integer NOT NULL DEFAULT 0,  -- vs previous rebuild
  computed_at     timestamptz NOT NULL,
  PRIMARY KEY (sport_id, scope, player_id)
);
CREATE INDEX rankings_board_idx ON rankings (sport_id, scope, rank);
§ 05

GraphQL surface

One schema, Relay connections for every list, and four types implementing Node — exactly the four deep-link targets the brief names.

Rules

RuleImplementationWhy it is not optional
Complexity limitgraphql-query-complexity, budget 1000A public mobile graph without a cost limit is a denial-of-service endpoint you shipped on purpose.
Depth limitmax depth 10Blocks recursive player → follows → player expansion.
Trusted documentsHash allowlist from client codegenIn production the app sends a hash, not a query string. Arbitrary queries are rejected; the hash also cuts request size on 3G.
Introspectionoff in productionThe committed SDL is the contract; the endpoint need not publish it.
PaginationRelay cursors, max first: 50Cursor pagination on (starts_at, id) stays correct while events are being published underneath the reader.
N+1DataLoader per requestLoaders are built in buildContext and die with the request, so no cross-user cache leak is possible.
Mutationsverb-first, payload typeregisterForEvent(input:) : RegisterForEventPayload with a typed userError field — expected failures are data, not exceptions.

Why entriesRemaining subtracts holds

If the card says two spots left and two people are already in checkout, the third player pays and then gets told the draw is full. Counting active seat holds against capacity means the badge, the registration button and the database agree — and the worst case becomes “shows full, briefly, then reopens” instead of “took money, then refunded.”

§ 06

Identity & authorization

Email-first: a six-digit code delivered by Resend. There is no SMS provider, and phone_e164 is optional, unverified contact information. Organizer is a grant on an event, not a role on a user.

OTP

  • Six digits, ten-minute TTL, argon2id-hashed at rest — a leaked otp_challenges table must not be a login.
  • Five verification attempts per challenge, then the challenge burns.
  • Rate limits, sliding window in Redis: 3 sends per email per 15 min, 20 per IP per hour, 200 per IP per day.
  • Delivery through Resend from a dedicated auth subdomain, with SPF, DKIM and DMARC published before launch. A hard bounce marks the address unusable rather than letting a user retry into a void.
  • The OTP funnel is a dashboard from day one — requested → delivered → verified. A drop in delivered-to-verified is a signup outage; without this instrumentation it presents as “conversion is down.”
  • Verification is constant-time and always takes the same path whether or not the email exists, so the endpoint cannot enumerate users.

Sessions

No roles in the JWT

An organizer’s permission is per-event and revocable. Baked into a 15-minute token, a revoked grant stays live for up to 15 minutes — on a screen that can rewrite match results. Grants are read from event_staff per request and memoized in a request-scoped loader. The cost is one indexed lookup; the benefit is that revocation is immediate.

Where authorization lives

In the service layer, not the resolver. Every service method that touches an event takes the actor and calls a policy function; the resolver’s Pothos authScopes is a cheap first gate, not the check that matters. This is what makes the same rule apply when a BullMQ job or the webhook handler calls the same service.

modules/tournament/service/policy.tsauthorization
export async function assertCanScore(actor: Actor, matchId: string) {
  const match = await repo.matchWithEvent(matchId);
  // 'owner' and 'manager' can do anything on their event;
  // 'scorer' is a volunteer at a single event, scoped to scoring only.
  const grant = await identity.grantsFor(actor.userId, match.eventId);
  if (!grant) throw forbidden();
  if (!['owner', 'manager', 'scorer'].includes(grant.role)) throw forbidden();
  if (match.status === 'completed' && grant.role === 'scorer') {
    // Corrections after the fact need a manager. A scorer can
    // mis-tap during a match; they should not rewrite a finished one.
    throw forbidden('CORRECTION_REQUIRES_MANAGER');
  }
  return match;
}

The hold, and why it is in Postgres

Capacity must be decided under a lock that also guarantees durability. A Redis counter is faster and will, on the one afternoon it drops a key, oversell a tournament that has physical courts. So: a row lock on the category, a count of confirmed entries plus live holds, and an insert that simply produces no row when the draw is full.

modules/registration/repo/hold.sqlcapacity reservation
-- Zero rows returned means "full". The caller maps that to
-- CATEGORY_FULL; no exception, no retry loop.
WITH locked AS (
  SELECT id, capacity FROM event_categories
   WHERE id = $1 FOR UPDATE
),
used AS (
  SELECT
    (SELECT count(*) FROM registrations
      WHERE event_category_id = $1
        AND status IN ('confirmed','checked_in','payment_pending')) AS taken,
    (SELECT coalesce(sum(seats),0) FROM seat_holds
      WHERE event_category_id = $1
        AND released_at IS NULL
        AND expires_at > now())                                    AS held
)
INSERT INTO seat_holds (id, event_category_id, registration_id, seats, expires_at)
SELECT $2, locked.id, $3, 1, now() + interval '10 minutes'
  FROM locked, used
 WHERE used.taken + used.held + 1 <= locked.capacity
RETURNING id, expires_at;

Two things release a hold: the delayed BullMQ job scheduled at creation, and the expires_at > now() predicate above, which means an expired hold stops blocking capacity the instant it expires even if the job has not run yet. The job exists to flip released_at and move the registration to expired, not to make capacity correct.

Doubles, and the partner who may not exist yet

The partner is invited by email address, which may belong to nobody yet. The invite row carries the address; if it signs up later, the invite binds to the new user on their first authenticated request. Because players know each other’s phone numbers rather than their email addresses, the invite field must also accept an existing PL4Y player chosen by in-app search — that is the mitigation for the friction this introduces, and the doubles funnel is the metric that says whether it worked. The captain pays for the team. Split payment is deferred — it adds a second payment state machine, a partial-refund policy, and a partner who can strand a confirmed entry by not paying.

No seat hold is taken while a registration waits for a partner. A 48-hour hold would let one player park a slot in a popular draw for two days. Capacity is reserved when the team becomes real.

Webhook handling

modules/payments/service/webhook.tsidempotent ingest
export async function razorpayWebhook(req: Request, res: Response) {
  // req.body is a Buffer here — see the middleware order in §02.
  const signature = req.get('x-razorpay-signature') ?? '';
  const expected = createHmac('sha256', config.RAZORPAY_WEBHOOK_SECRET)
    .update(req.body).digest('hex');
  if (!timingSafeEqual(Buffer.from(expected), Buffer.from(signature))) {
    return res.status(400).send('bad signature');
  }

  const event = JSON.parse(req.body.toString('utf8'));

  // Claim the event id first. A duplicate delivery inserts nothing
  // and returns 200, so Razorpay stops retrying immediately.
  const claimed = await db.paymentWebhookEvent.createMany({
    data: [{ razorpayEventId: event.id, eventType: event.event, payload: event }],
    skipDuplicates: true,
  });
  if (claimed.count === 0) return res.status(200).send('duplicate');

  // Ack fast; Razorpay times out at 5s and retries. The state change
  // happens in a job that can take as long as it needs.
  await queue.payments.add('apply-webhook', { eventId: event.id });
  return res.status(200).send('ok');
}
Two invariants worth writing tests for first

Confirmed entries never exceed capacity. Test: fire fifty concurrent registrations at a ten-entry category and assert exactly ten confirm.
One captured payment produces exactly one confirmed registration. Test: deliver the same payment.captured webhook five times and assert one payment row, one ledger entry, one push.

Reconciliation

Webhooks get lost. A repeatable job sweeps every payment_pending registration older than 30 minutes, queries the Razorpay Orders API for the true status, and drives the state machine from the answer. This is the safety net that turns a missed webhook from a support ticket into a 30-minute delay, and it is Phase 1 work, not a later hardening task.

§ 08

Tournament engine

Single elimination with a Plate, which is what the brief's bracket screen shows. Both brackets are generated in one pass, and every match knows where its winner and its loser go before a single point is played.

Draw generation

  1. Take confirmed registrations for the category, ordered by rating descending; unrated entries sort last with a deterministic tiebreak on registration time.
  2. Bracket size is the next power of two. Byes go to the top seeds and are represented as real match rows with one side null and status = 'walkover' — a bye is a result, not a missing row, so advancement logic has no special case.
  3. Seeds are placed by standard bracket positions (1 vs 16, 8 vs 9, ...), so the top two seeds can only meet in the final.
  4. The Plate bracket is sized to the number of first-round losers. Championship round-1 matches get loser_match_id pointing into Plate round 1.
  5. The whole draw — both brackets and all wiring — is written in one transaction. A partially generated draw is not a state the system can be in.

Advancement

Because the wiring is precomputed, confirming a result is a single write with no traversal:

modules/tournament/service/advance.tsresult confirmation
await db.$transaction(async (tx) => {
  // Serialize advancement per tournament. Two courts finishing at the
  // same instant must not write the same next-match slot concurrently.
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(hashtext(${tournamentId}))`;

  const m = await tx.match.findUniqueOrThrow({ where: { id: matchId } });
  if (m.status === 'completed') return;          // idempotent by design

  await tx.matchResult.create({ data: result });
  await tx.match.update({ where: { id: matchId }, data: { status: 'completed' } });

  // Winner up the championship; loser across to the plate, if wired.
  if (m.winnerMatchId) await placeSide(tx, m.winnerMatchId, m.winnerSlot, winnerId);
  if (m.loserMatchId)  await placeSide(tx, m.loserMatchId,  m.loserSlot,  loserId);

  // Outbox, drained by the worker: rating, standings, push, Pusher.
  await tx.outbox.createMany({ data: [
    { topic: 'match.completed', payload: { matchId, tournamentId } },
  ]});
});

Scheduling onto courts

A greedy assigner, run whenever a match becomes ready, with two constraints that matter to players standing on a court:

  • Minimum rest — no player is assigned a match starting less than min_rest_minutes (default 20) after their previous one ends.
  • Round ordering — every round-n match is scheduled before any round-n+1 match on the same court, so the bracket cannot deadlock waiting on itself.

The output is advisory: organizers reassign courts by hand constantly, and the API allows it. The scheduler removes typing, it does not own the schedule.

§ 09

Live scoring over Pusher

One rule holds the whole design together: Pusher is a transport for cache invalidation, never a source of truth. Every payload is self-contained and carries a sequence number, so a dropped message costs a refetch and never leaves a stale score on screen.

Channel topology

ChannelCarriesSubscribersVolume
presence-event-{id}Match status transitions, standings, bracket advancesEveryone with the event open — hundredsLow tens per event
private-match-{id}Point-by-point scoreOnly viewers who opened that match — typically single digitsHigh ~50 per match
private-user-{id}Registration confirmed, your match is on court 3, ranking movedOne device setLow
The split is a cost decision, and it is the one that will surprise you

A 32-entry draw is 31 championship matches plus 15 in the Plate. At roughly 50 rallies per best-of-three, that is about 2,300 point events per event day. Delivery is metered per subscriber: broadcast every point to an event-wide channel with 200 people watching and you generate ~460,000 delivered messages in one afternoon. Keeping point-level detail on private-match-{id}, where the audience is the handful of people actually watching that court, is what keeps the same day in the low tens of thousands. Confirm the current metering against your Channels plan before launch — but design for the split regardless.

Write path

modules/scoring/service/recordPoint.tspoint ingest
export async function recordPoint(actor: Actor, input: RecordPointInput) {
  const match = await assertCanScore(actor, input.matchId);

  return db.$transaction(async (tx) => {
    // Optimistic concurrency: two scorers on two devices cannot both
    // write seq 41. The loser retries against fresh state.
    const next = match.scoreSeq + 1;
    if (input.expectedSeq !== match.scoreSeq) throw conflict('SCORE_STALE');

    const state = applyPoint(match.currentScore, input.side,
                             await sport.scoringRuleFor(match.sportId));

    await tx.matchScoreEvent.create({ data: {                // append-only
      matchId: match.id, seq: next, kind: 'point',
      scoringSide: input.side, stateAfter: state, recordedBy: actor.userId,
    }});
    await tx.match.update({ where: { id: match.id },
      data: { currentScore: state, scoreSeq: next,
              status: state.matchOver ? 'awaiting_confirm' : 'live' }});

    // Fan-out never happens inline. It goes through the outbox so a
    // Pusher outage cannot fail the scorer's tap.
    await tx.outbox.create({ data: { topic: 'match.score', payload: {
      matchId: match.id, seq: next, state, eventId: match.eventId,
    }}});

    return state;
  });
}

Fan-out, throttled

The worker drains outbox and publishes with a per-match coalescing window of 250 ms. Within a window only the latest state is sent, because the payload is the whole score rather than a delta — two rapid points collapse into one message with no information lost. Match-status transitions bypass the window: “this match is now live” should not wait.

Correctness under a flaky network

  • Every payload carries seq. The client tracks the last seq per channel; on a gap or a reconnect it refetches match(id) over GraphQL and resumes. Pusher is never trusted to have delivered everything.
  • Because state is complete rather than a delta, a client that misses ten messages and receives the eleventh is fully correct.
  • If Pusher is unreachable, a feature flag drops clients to polling match(id) every five seconds. Degraded, not broken.
  • The scoring device works offline: points queue locally against expectedSeq and replay on reconnect. A conflict surfaces the server state and asks the scorer to confirm — the one place in the system where a human resolves a merge.
§ 10

Rating & rankings

Glicko‑2 per player per sport, written append-only, with rankings as a cache rebuilt on write. The algorithm is replaceable; the log is not.

Why not Elo

Amateur players do not play continuously — they play four matches on a Saturday and then nothing for six weeks. Elo has no memory of that gap and treats a rating from March as being exactly as reliable as one from yesterday. Glicko‑2 carries a rating deviation that grows with inactivity, so a returning player’s rating moves quickly to find its level again, and a regular’s does not swing on one upset. That behaviour is the difference between a leaderboard players trust and one they dismiss.

Two numbers, honestly labelled

Glicko‑2 is defined over rating periods, batching results. Players want their rating to move the moment they win. Both, then:

ValueComputedShown as
provisionalImmediately after each confirmed result, single-match updateThe number that moves on the Match Detail screen, marked provisional
settledWeekly period job, Monday 03:00 IST, over all matches since the last periodThe rating on the profile and the only input to rankings

Provisional rows are written with is_provisional = true and superseded when the period runs. Both are in the same log, so the history a player sees is continuous.

Doubles

The launch sport is mostly doubles, and Glicko‑2 is a singles model. The documented rule:

  • A team’s rating is the mean of its members; its RD is the root-mean-square of theirs.
  • The team-level delta is computed once, then split between partners inversely to their RD — the less certain player absorbs more of the change, which is what RD means.
  • A match against a team more than 400 points below yours contributes at reduced weight, so stacking easy draws cannot inflate a ranking.

This is a defensible v1, not a solved problem. It lives behind algo_version = 'glicko2-v1', and replacing it means writing glicko2-v2 and replaying the log — no migration, which is precisely what the brief asked the schema to preserve.

Rankings cache

modules/rating/service/rebuild.tsleaderboard rebuild
// Rebuilt after each rating period and when an event completes.
// Scopes are enumerated, not arbitrary: national, per city, per age band.
INSERT INTO rankings (sport_id, scope, player_id, rank, rating, matches_played, movement, computed_at)
SELECT $1, $2, ps.player_id,
       dense_rank() OVER (ORDER BY ps.rating DESC NULLS LAST),
       ps.rating, ps.matches_played,
       coalesce(prev.rank, 0) - dense_rank() OVER (ORDER BY ps.rating DESC NULLS LAST),
       now()
  FROM player_sports ps
  JOIN player_profiles pp ON pp.id = ps.player_id
  LEFT JOIN rankings prev
    ON prev.sport_id = $1 AND prev.scope = $2 AND prev.player_id = ps.player_id
 WHERE ps.sport_id = $1
   AND ps.matches_played >= 5        -- unranked below this; shown as "unranked"
   AND pp.city = $3
ON CONFLICT (sport_id, scope, player_id) DO UPDATE
   SET rank = EXCLUDED.rank, rating = EXCLUDED.rating,
       movement = EXCLUDED.movement, computed_at = EXCLUDED.computed_at;

The Rankings screen reads a Redis copy of the top 200 per scope, refreshed by the same job, and falls through to the replica for deep pages. A five-match minimum keeps a single lucky win off the leaderboard, and movement gives the screen its up/down arrow without a second query.
