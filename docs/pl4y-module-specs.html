Each spec below is a ticket-ready contract. Rules are numbered R1, R2… per module so a test, a PR and a bug report can all point at the same line — registration R4 means one thing and only one thing.

Three conventions hold across every module. The service interface is the module’s only public surface — everything else in the directory is private, including its repository. Errors listed as user are typed fields in a mutation payload; errors listed as system are GraphQL errors with a code. And every module owns its tables exclusively: where a module needs to change another’s data, it calls a named service method, which is why rating writes a player’s rating through profile.applyRating() rather than through an UPDATE.

Dependency layers & build order

Arrows are dependency direction, which is also build order — a layer cannot be finished before the one above it. Sn is the sprint from the brief’s Section 8. Orange marks the modules carrying real risk: money, capacity and concurrency.

01

identity

Sprint 1

Who a user is, how they prove it, and what they are allowed to do. Email-first, verified by a six-digit code through Resend; there is no SMS provider. Organizer permission is a grant on an event, never a role on a person.

4 tablesdepends on nothingblocks everything

Owns

users · otp_challenges · refresh_tokens · event_staff

Service interface

requestOtp(email: string, purpose: OtpPurpose)    => { challengeId, retryAfterSeconds }
verifyOtp(email: string, code: string, device?)   => { access, refresh, isNewUser }
rotateSession(refreshToken: string)              => { access, refresh }
revokeSession(actor: Actor, sessionId: string)    => void
revokeAllSessions(userId: string)                 => void
grantsFor(userId: string, eventId: string)        => Grant | null
grantsForUser(userId: string)                     => Grant[]
addStaff(actor, eventId, userId, role)            => Grant
suspend(actor: AdminActor, userId, reason)        => void

GraphQL

Query.me: Viewer
Mutation.requestOtp(email: String!): RequestOtpPayload!
Mutation.verifyOtp(email: String!, code: String!): VerifyOtpPayload!
Mutation.refreshSession(refreshToken: String!): RefreshSessionPayload!
Mutation.logout(allDevices: Boolean = false): LogoutPayload!
Mutation.addEventStaff(input: AddEventStaffInput!): AddEventStaffPayload!

Rules

  1. OTP is six digits, argon2id-hashed at rest, ten-minute TTL. The plaintext code is never stored or logged.
  2. Five verification attempts per challenge, then the challenge is burned regardless of remaining TTL.
  3. Send limits, sliding window in Redis: 3 per email per 15 minutes, 20 per IP per hour, 200 per IP per day. Exceeding any returns OTP_THROTTLED with retryAfterSeconds.
  4. Verification takes the same code path and the same time whether or not the email exists. Addresses are normalised and stored as citext, so one inbox is one account. The endpoint must not be a user-enumeration oracle.
  5. Access tokens are RS256 JWTs valid 15 minutes, carrying sub, sid, ver and no role or grant claim.
  6. Refresh tokens are opaque 256-bit values stored hashed, valid 60 days, and rotate on every use.
  7. Presenting a refresh token that has already been spent revokes the entire family_id. Every device in that lineage must log in again.
  8. A user with status != 'active' cannot be issued tokens; existing sessions are revoked on suspension.
  9. The first successful verifyOtp for an email creates the users row and the player_profiles row in one transaction. A user without a profile is not a state the system can be in.
  10. Grants are read from event_staff per request and memoised in a request-scoped loader. Never cached across requests — revocation must be immediate.

Emits

  • user.created → profile, notifications
  • user.suspended → registration
  • staff.granted → notifications

Jobs

  • purge-expired-otp — hourly
  • purge-revoked-tokens — daily, 90-day retention

Errors

  • OTP_INVALID user
  • OTP_EXPIRED user
  • OTP_THROTTLED user — carries retry seconds
  • SESSION_REUSE_DETECTED system
  • ACCOUNT_SUSPENDED system
Done when

A real inbox receives a code and exchanges it for a token pair; replaying a spent refresh token forces re-login on both devices in the family; and an organizer whose event_staff row is deleted loses access on their very next request, not up to fifteen minutes later.

02

sport

Sprint 2

The registry that makes multi-sport real rather than aspirational. Scoring rules live here as data, which is what keeps if (sport === 'pickleball') out of the scoring module.

4 tablesread-mostlyseeded, not user-generated

Owns

sports · formats · skill_bands · scoring_rules

Service interface

list()                                        => Sport[]
bySlug(slug: string)                           => Sport
formatsFor(sportId: string)                    => Format[]
skillBandsFor(sportId: string)                 => SkillBand[]
scoringRuleFor(sportId: string, formatId?)     => ScoringRule

The shape that matters

ScoringRule is the contract between this module and scoring. Get it right and a second sport is a row; get it wrong and it is a refactor.

type ScoringRule = {
  pointsToWin: number;             // pickleball: 11
  winBy: number;                   // 2
  hardCap: number | null;          // 15 — or null for unlimited deuce
  gamesToWin: number;              // 2, i.e. best of 3
  serveModel: 'rally' | 'side_out';
  decidingGame?: {                 // third game is often shorter
    pointsToWin: number;           // 15
    hardCap: number | null;        // 21
  };
  switchEndsAt?: number;           // 6, in the deciding game
};

// Seed row for launch. A second sport is INSERT, not a code change.
{ slug: 'pickleball', name: 'Pickleball',
  formats: ['singles','doubles','mixed_doubles'],
  skillBands: ['2.5','3.0','3.5','4.0','4.5','5.0+'],
  scoringRule: { pointsToWin: 11, winBy: 2, hardCap: 15, gamesToWin: 2,
                 serveModel: 'rally',
                 decidingGame: { pointsToWin: 15, hardCap: 21 },
                 switchEndsAt: 6 } }

Rules

  1. Every sport, format, skill band and scoring rule is seed data under version control. No runtime writes in Phase 1.
  2. Skill bands are per sport. Pickleball uses the DUPR-style 2.5–5.0+ ladder; another sport will not, and nothing may assume that scale.
  3. Sports are soft-disabled with an active flag, never deleted — historical matches must keep resolving.
  4. Results are cached in-process for the process lifetime. This table changes on deploy, not at runtime.
Done when

Inserting a second sport row with its formats, bands and scoring rule makes that sport appear in Explore filters, ranking tabs, profile sport selection and event creation — with zero code changes. That is the multi-sport acceptance test, and it should be run once in Sprint 2 with a throwaway sport rather than discovered in year two.

03

profile

Sprint 2

The player as other players see them: sports, skill, location, results, achievements, follows. Also the read model behind the Home screen’s stats snapshot.

4 tablesdepends on identity, sportread-heavy

Owns

player_profiles · player_sports · achievements · follows

Service interface

byUserId(userId: string)                          => PlayerProfile
publicView(viewerId: string | null, playerId)     => PublicProfile
updateSports(actor, [{ sportId, skillBand }])      => PlayerProfile
updateLocation(actor, { city, geo })              => PlayerProfile
avatarUploadUrl(actor, contentType)               => { url, key, expiresAt }
setAvatar(actor, key: string)                     => PlayerProfile
follow(actor, playerId) / unfollow(actor, playerId) => FollowState
statsSnapshot(playerId, sportId)                  => StatsSnapshot
// Called by the rating module. The ONLY way rating columns change.
applyRating(playerId, sportId, { rating, rd, volatility, matches })

Rules

  1. A profile is created in the same transaction as its user, by identity. This module never creates one.
  2. At least one sport must be selected before a player can register for an event. Onboarding enforces it; the API enforces it again.
  3. skill_band is self-declared at onboarding and stays editable; rating is derived and read-only to the player. Never conflate them in the UI or the schema.
  4. Visibility is one of public, players_only, private. publicView returns null for hidden fields rather than erroring — a private profile must not be distinguishable from a missing one.
  5. Results are always visible on a profile that appears in a public draw. You cannot enter a public tournament and hide the outcome.
  6. Avatars upload directly to Cloudinary under a server-issued signature; only the public_id is stored, and the server checks that the returned id matches the one it signed. Display URLs come from named transformations and are never persisted.
  7. Following is one-directional and requires no approval. Self-follow is rejected.
  8. statsSnapshot is materialised on match completion, not computed per request. The Home screen must not run six aggregates.

Emits

  • profile.sports_changed → rating
  • follow.created → notifications
  • achievement.earned → notifications

Errors

  • PROFILE_NOT_FOUND user
  • NO_SPORT_SELECTED user
  • CANNOT_FOLLOW_SELF user
  • INVALID_SKILL_BAND user — band not valid for that sport
Done when

The same playerProfile(id:) query returns full fields to the owner and null-filled fields to a stranger on a private profile, and one home query fills every region of the Home screen without a second round trip.

04

venues

Sprint 3

Where play happens. Deliberately thin: courts exist so a tournament can be scheduled onto them, and so a player can find a place to play. No booking, no inventory, no availability calendar.

2 tablesno dependenciesbooking is Phase 3

Owns

venues · venue_courts

Service interface

search({ near?: GeoPoint, radiusKm?, city?, sportId? }, page)  => Page<Venue>
byId(venueId: string)                                       => Venue
courtsFor(venueId: string)                                  => Court[]
create(actor: OrganizerActor, input)                         => Venue

Rules

  1. Radius search uses the PostGIS gist index on geo, capped at 50 km. An uncapped radius query is a table scan wearing a filter.
  2. A court belongs to exactly one venue and carries surface, indoor and sport_ids[] — one court often serves several sports.
  3. Venues are created by organizers and are visible to everyone. Moderation is manual in Phase 1, which is acceptable at this volume and should be revisited before it is not.
  4. Court availability in Phase 1 means only “is this court already assigned to another match in this tournament”. It is a scheduling concept, not a booking one.
Done when

A venue with four courts can be created, found by a 10 km radius query from a map centre, and its courts assigned to matches by the tournament scheduler without double-booking a court inside one event.

05

events

Sprint 3

The thing a player discovers, and the categories they actually register for. Owns capacity and the single price-quote function that both registration and payments call — so what the player agreed to and what Razorpay charges cannot drift.

3 tablesdepends on sport, venues, identityhighest read volume

Owns

events · event_categories · event_media

Service interface

search(filter: EventFilter, page: CursorPage)      => Page<Event>
bySlug(slug: string)                              => Event
create(actor: OrganizerActor, input)               => Event
update(actor, eventId, patch)                     => Event
publish(actor, eventId)                           => Event
cancel(actor, eventId, reason)                    => Event
capacityOf(categoryId)                            => { capacity, taken, held, remaining }
priceQuote(categoryId)                            => PriceQuote
markLive(eventId) / markCompleted(eventId)        => Event

Lifecycle

draft ──publish──▶ published ──first match starts──▶ live ──▶ completed
  │                   │
  └──────────────── cancelled ◀───────────────────────────────┘
                        │
                        └─▶ triggers payments.bulkRefund() for every
                            confirmed registration on the event

Rules

  1. Publishing requires at least one category, a city or venue, and registration_closes_at < starts_at. Publish is the validation gate; drafts may be incomplete.
  2. Once published, starts_at, fees and capacity may only be changed while a category has zero confirmed registrations. After that they are frozen — players agreed to specific terms.
  3. priceQuote is the only place money is computed: entry + platform fee + tax(bps). The client never calculates a total, and payments calls this same function when creating an order.
  4. Availability is derived, never stored: remaining ≤ 0 → FULL, remaining ≤ 10% of capacity → ALMOST_FULL, past registration_closes_at → CLOSED.
  5. capacityOf subtracts live seat holds as well as confirmed entries, so the badge on a card and the outcome of pressing Register agree.
  6. Discovery reads only touch the partial index on status IN ('published','live'). Draft and cancelled events are not in the index and are never listed.
  7. Cancelling an event is irreversible and enqueues a full refund for every confirmed registration, platform fee included.
  8. The slug is permanent once published — it is a deep link that will exist in someone’s WhatsApp forever.

Emits

  • event.published → notifications
  • event.cancelled → payments, notifications
  • event.live → notifications
  • category.full → notifications (waitlist)

Jobs

  • close-registration — delayed to registration_closes_at
  • refund-under-minimum — at close, if entries < minimum

Errors

  • EVENT_NOT_FOUND user
  • REGISTRATION_CLOSED user
  • INVALID_EVENT_WINDOW user
  • EVENT_HAS_ENTRIES user — on a frozen-field edit
  • FORBIDDEN system — not staff on this event
Done when

Explore returns correct results for a filter combining sport, city, date range, skill band and price, at p95 under 200 ms against 10,000 seeded events — and the price shown on the confirm screen is byte-identical to the amount Razorpay is asked to charge.

06

registration

Sprint 4Highest risk

The five-step flow from the brief, as one state machine. Three failure modes here cost real money: overselling a draw with physical courts, double-charging a player, and a partner who never accepts.

5 tablesdepends on events, payments, profilewrite TDD first

Owns

registrations · teams · team_members · registration_invites · seat_holds

Service interface

begin(actor, { eventCategoryId })              => Registration
invitePartner(actor, { registrationId, email }) => Invite
acceptInvite(actor, token: string)             => Registration  // takes the hold
declineInvite(actor, token: string)            => void
confirmFromPayment(paymentId: string)          => Registration  // payments calls this
failFromPayment(paymentId, reason)             => Registration
expireHold(holdId: string)                     => void          // job calls this
cancel(actor, registrationId)                  => Registration
checkIn(actor, registrationId)                 => Registration
listForEvent(actor, eventId, filter, page)     => Page<Registration>
confirmedForCategory(categoryId)               => Registration[] // tournament calls this

Rules

  1. A player may hold at most one live entry per category. Enforced by a unique partial index, not by a read-then-write check.
  2. No seat hold is taken while a registration awaits a partner. A 48-hour hold would let one player park a slot in a popular draw for two days.
  3. The hold TTL is 10 minutes; the partner invite TTL is 48 hours. Both are config, not literals.
  4. Capacity is decided inside a transaction that takes FOR UPDATE on the category row and counts confirmed entries plus unexpired holds. An insert that would exceed capacity returns zero rows, which maps to CATEGORY_FULL.
  5. An expired hold stops blocking capacity the instant it expires, because the count predicate is expires_at > now(). The release job flips released_at and moves the registration to expired; it is not what makes capacity correct.
  6. The captain pays for the whole team. Split payment is deferred — it needs a second payment state machine and lets a partner strand a confirmed entry.
  7. A partner must satisfy the category’s skill and age constraints. Validated at accept, not at invite, because the partner may not have had an account at invite time.
  8. Payment failure leaves the hold alive until its TTL so a retry does not lose the slot. Only expiry releases it.
  9. Cancelling after cancellation_cutoff_at refunds nothing but still returns the slot to the pool and promotes the waitlist. Punishing the player should not punish the draw.
  10. Check-in is allowed only within two hours either side of the event start, and only for confirmed entries.
  11. Every transition goes through one guard function that consults the transition table. There is no other way to write registrations.status, and a disallowed transition throws rather than silently no-ops.

07

payments

Sprint 4Highest risk

Razorpay orders, webhook ingest, refunds and a ledger. Knows nothing about tournaments — it moves money against a registration id and tells the registration module what happened.

5 tablesdepends on nothingthe webhook is the truth

Owns

payment_orders · payments · refunds · payment_webhook_events · ledger_entries

Service interface

createOrder(actor, registrationId)                 => { orderId, amountPaise, key }
ingestWebhook(rawBody: Buffer, signature: string)  => { accepted: boolean }
applyWebhook(razorpayEventId: string)              => void   // job, not request
refund(actor, paymentId, amountPaise, reason)      => Refund
bulkRefund(eventId, reason)                       => { queued: number }
reconcilePending()                                => { resolved: number }
ledgerFor(registrationId)                          => LedgerEntry[]
receipt(actor, paymentId)                          => Receipt  // rendered, not stored

Rules

  1. The order amount is recomputed server-side from events.priceQuote() at order creation. An amount arriving from a client is ignored, not validated.
  2. The webhook route receives the raw body. HMAC-SHA256 with a timing-safe comparison; a bad signature is a 400 and nothing is written.
  3. Ingest claims razorpay_event_id as a primary key before doing anything. A duplicate delivery inserts nothing and returns 200 immediately, so Razorpay stops retrying.
  4. Ingest acknowledges in under one second and does the state change in a job. Razorpay times out at five seconds and will retry a slow success.
  5. A registration confirms only on a verified payment.captured, or on reconciliation against the Orders API. The client-side checkout callback is a UI hint and confirms nothing.
  6. Every money movement writes a ledger_entries row — charge, platform fee, tax, refund, reversal. The ledger, not the payments table, is what reconciles against a Razorpay settlement report.
  7. Refunds are idempotent on (payment_id, reason, amount_paise) unless an explicit idempotency key is supplied. Retrying a refund must never send money twice.
  8. A refund may never exceed captured − already_refunded. Enforced by a check against the sum, inside the transaction.
  9. Reconciliation runs every 15 minutes over every payment_pending registration older than 30 minutes, queries Razorpay for truth, and drives the state machine from the answer. This is Phase 1 work, not later hardening.
  10. Raw gateway payloads are stored on the payment row. When a player disputes a charge in four months, that payload is the evidence.
  11. Receipts are rendered on demand, never stored as files. receipt() builds the document from ledger_entries; the app renders it and the confirmation email embeds it inline. No PDF, no bucket, no signed file URL — Cloudinary is for images, and the ledger is already the source of truth, so a stored file would only be a second copy that can disagree with it.
  12. Payment emails — confirmation, failure, refund processed — are sent through the Resend adapter by this module. notifications owns the in-app feed and push; transactional email belongs to the module that owns the action. Each payment email is still paired with a notifications.emit() so the feed stays complete.
When receipts become invoices

If GST rules require a numbered tax invoice retained as a document, that is the point to add object storage for non-image artefacts — not to reach for Cloudinary. Add an invoices table with a sequential number at the same time: a receipt you can re-render is not the same thing as an invoice you must reproduce byte-for-byte.

Refund policy, as data

Cancel before cancellation_cutoff_at: entry fee refunded, platform fee retained — and disclosed in the quote at checkout. Cancel after: nothing refunded, slot still returns. Organizer cancels the event, or a category misses its minimum: full refund including the platform fee. Withdrawal after the draw is at organizer discretion, and the opponent receives a walkover that does not affect either rating.

Emits

  • payment.captured → registration, notifications
  • payment.failed → registration, notifications
  • refund.processed → notifications

Jobs

  • apply-webhook — 5 retries, then page
  • reconcile-pending — every 15 min
  • process-refund — 5 retries, then page

Errors

  • PAYMENT_FAILED user
  • ORDER_ALREADY_PAID user
  • REFUND_WINDOW_CLOSED user
  • REFUND_EXCEEDS_CAPTURED system
  • BAD_SIGNATURE system — 400, never 500
  • GATEWAY_UNAVAILABLE system
Done when

A test-mode UPI payment confirms an entry end to end; five duplicate webhook deliveries produce exactly one payment, one ledger entry and one push; a deliberately dropped webhook is resolved by reconciliation within 30 minutes with no human involved; and the count of payment_pending older than 30 minutes sits at zero on the operations dashboard.

08

rating

Sprint 6

Glicko-2 per player per sport, written append-only, with rankings as a cache rebuilt on write. The algorithm is replaceable; the log is not.

3 tablesdepends on scoring, profileappend-only

Owns

rating_events · rating_periods · rankings

Service interface

applyMatch(matchId: string)                        => RatingEvent[]  // provisional
runPeriod(periodId: string)                        => { playersUpdated: number }
rebuildRankings(sportId, scope: RankingScope)      => { ranked: number }
ratingFor(playerId, sportId)                       => { rating, rd, provisional }
historyFor(playerId, sportId, page)                => Page<RatingEvent>
leaderboard(sportId, scope, page)                  => Page<RankingRow>
replay(sportId, fromDate, algoVersion)             => void  // backfill only

Rules

  1. Ratings are Glicko-2, not Elo. Rating deviation grows with inactivity, which is the only honest way to rate players who compete in bursts around tournaments.
  2. Two numbers exist and are labelled differently in the UI. Provisional is a single-match update applied the moment a result is confirmed. Settled comes from the weekly period job and is the only input to rankings.
  3. Provisional rows carry is_provisional = true and are superseded when the period runs. Both live in the same log so a player’s history reads continuously.
  4. The rating period runs weekly, Monday 03:00 IST, over every match confirmed since the previous period.
  5. For doubles, a team’s rating is the mean of its members and its RD the root-mean-square of theirs. The team-level delta is split between partners inversely to their RD — the less certain player absorbs more of the change.
  6. A win against a team rated more than 400 points below yours contributes at reduced weight, so stacking soft draws cannot inflate a ranking.
  7. Walkovers, retirements and forfeits do not affect either player’s rating. Only outcome = 'played' reaches the engine.
  8. Every row carries algo_version. Replacing the model means writing glicko2-v2 and replaying the log — no migration, which is the whole point of the append-only design.
  9. A player needs five settled matches in a sport before appearing in rankings; below that the profile shows unranked rather than a misleading number.
  10. Ranking scopes are enumerated, not arbitrary: national, city:<name>, age:<band>. An open-ended scope string is an unbounded table.
  11. movement is computed against the previous rebuild and stored, so the leaderboard’s up/down arrow costs no second query.
  12. Ratings are written to player_sports only through profile.applyRating(). This module never issues an UPDATE against another module’s table.

Emits

  • rating.changed → notifications
  • ranking.moved → notifications (threshold: 5 places)

Jobs

  • apply-provisional — on result confirmed
  • run-period — weekly, Mon 03:00 IST
  • rebuild-rankings — after period, and on event completion

Errors

  • RATING_UNAVAILABLE user — fewer than 5 matches
  • PERIOD_ALREADY_RUN system
  • UNKNOWN_ALGO_VERSION system
Done when

The seeded 32-entry tournament produces a ranked leaderboard with correct movement arrows — and a determinism test passes: replaying the entire rating_events log under the same algo_version reproduces every current rating to the last decimal. Without that test, “swappable algorithm” is a claim rather than a property.

09

tournament

Sprint 8Concurrency

Draw generation with Championship and Plate, court scheduling, and advancement. Every match knows where its winner and its loser go before a single point is played.

3 tablesdepends on events, registrationadvisory-locked

Owns

tournaments · matches · court_assignments

Service interface

generateDraw(actor, { eventCategoryId })         => Tournament
regenerateDraw(actor, tournamentId)             => Tournament  // pre-first-match only
schedule(tournamentId)                          => CourtAssignment[]
assignCourt(actor, matchId, courtId, startsAt)  => Match       // manual override
advance(matchId, result: MatchResult)           => void        // scoring calls this
bracketFor(eventCategoryId)                     => Bracket
standingsFor(eventCategoryId)                   => StandingRow[]
liveMatches(eventId)                            => Match[]

Draw generation

  1. Only confirmed and checked_in registrations enter a draw. A payment still pending at draw time is not in the tournament.
  2. Seeding is by settled rating descending; unrated entries sort last, tie-broken deterministically by confirmation time so a regenerated draw is reproducible.
  3. Bracket size is the next power of two. Byes go to the top seeds and are written as real match rows with one side null and status = 'walkover' — a bye is a result, so advancement has no special case.
  4. Seeds are placed by standard bracket positions (1 v 16, 8 v 9, …), so the top two seeds can only meet in the final.
  5. The Plate is sized to the number of first-round losers, and Championship round-1 matches carry loser_match_id pointing into Plate round 1. Both brackets and all wiring are generated in one pass.
  6. The whole draw is written in one transaction. A partially generated draw is not a state the system can be in.
  7. A draw requires at least four entries. Below that, the category is refunded rather than played.
  8. Once any match has left scheduled, the draw is immutable. regenerateDraw throws DRAW_LOCKED.

Advancement & scheduling

  1. Advancement takes a per-tournament pg_advisory_xact_lock. Two courts finishing simultaneously must not write the same next-match slot concurrently.
  2. Advancing an already-completed match is a no-op, not an error. The operation is idempotent because it is reachable from a retried job.
  3. The scheduler is greedy, re-run whenever a match becomes ready, and respects a minimum rest of 20 minutes between a player’s matches.
  4. Every round-n match is scheduled before any round-n+1 match on the same court, so a bracket cannot deadlock waiting on itself.
  5. The schedule is advisory. Organizers reassign courts by hand constantly and the API allows it — the scheduler removes typing, it does not own the schedule.

Emits

  • draw.generated → notifications
  • match.ready → notifications, realtime
  • match.completed → rating, realtime
  • tournament.completed → rating, events

Errors

  • INSUFFICIENT_ENTRIES user
  • DRAW_ALREADY_GENERATED user
  • DRAW_LOCKED user
  • COURT_DOUBLE_BOOKED user
  • MATCH_NOT_READY system
Done when

A 32-entry draw generates 31 Championship matches and 15 Plate matches with complete winner and loser wiring; scoring every match to completion leaves exactly one Championship winner, one Plate winner, and zero unfilled slots; and two matches confirmed in the same millisecond both advance correctly.

scoring

Sprint 8Concurrency

Live score capture on a court-side device, an append-only event log, and result confirmation. The scoring rules come from the sport module — this module knows how to count, not what counting means.

2 tablesdepends on tournament, sportoffline-tolerant

Owns

Service interface

confirmResult(actor, matchId)                     => MatchResult
disputeResult(actor, matchId, reason)             => MatchResult
timeline(matchId)                                 => ScoreEvent[]

Rules

  1. Every write carries expectedSeq. If it does not match matches.score_seq, the write is rejected with SCORE_STALE and the caller re-reads. Two scorers on two devices cannot both write sequence 41.
  2. match_score_events is append-only. An undo is a new event of kind undo, never a delete — the timeline is evidence.
  3. Each event stores state_after as the complete score, not a delta. A client that missed ten messages is correct on receiving the eleventh.
  4. Point validity — when a game ends, whether a hard cap applies, who serves — is decided entirely by the ScoringRule fetched from sport. No sport-specific branch exists in this module.
  5. Fan-out is never inline. The transaction writes an outbox row; a Pusher outage cannot fail a scorer’s tap.
  6. A completed match moves to awaiting_confirm, not completed. Confirmation comes from the opposing captain, or from an organizer override after 15 minutes.
  7. Correcting an already-confirmed result requires an owner or manager grant. A volunteer scorer can mis-tap during a match; they must not be able to rewrite a finished one.
  8. A correction that changes the winner reverses the advancement and the rating events before applying the new result. Both are in one transaction under the tournament advisory lock.
  9. The scoring device works offline: points queue locally against expectedSeq and replay on reconnect. A conflict surfaces the server state and asks the scorer to confirm — the one place in this system where a human resolves a merge.
  10. Walkovers, retirements and forfeits are submitted as outcomes without a point log, and are excluded from rating by rating R7.

  • match.score → realtime (throttled 250 ms)
  • match.live → realtime (immediate)
  • result.submitted → notifications
  • result.confirmed → tournament, rating

Errors

  • SCORE_STALE user — carries server state
  • MATCH_NOT_LIVE user
  • RESULT_ALREADY_CONFIRMED user
  • CORRECTION_REQUIRES_MANAGER system
Done when

Two devices score the same match and the second is rejected with the server state rather than overwriting it; a device scores five points offline and replays them cleanly on reconnect; and a spectator on another network sees a point land within 500 ms.
