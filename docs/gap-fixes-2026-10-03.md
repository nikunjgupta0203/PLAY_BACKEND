## Part A — Critical (money is lost or owed)

### 1. Hosts never get paid for finished events

**What's wrong**
When the last match of a tournament ends, the code only writes a log line. Nobody marks the **event** as `completed`, so the step that schedules the host's payout never runs.

**Example**
Riya hosts a badminton event: 32 players × ₹500. The final is played on Sunday. Her payout should go out on Wednesday (72 h later). It never does. The event shows "live" forever and her ₹16,000 (minus commission) sits with us.

**Fix**
When a tournament (one category's draw) completes, check whether **every** category of the event is now finished (`completed` or `cancelled`). If so, mark the event completed. That already emits `event.completed`, which schedules the payout.

A daily sweep should also complete events whose `endsAt` passed more than a day ago. Without it, an event where the host never entered scores would never get paid out.

**Code** (`src/worker.ts`)
```ts
'tournament.completed': async (payload) => {
  const eventId = String(payload['eventId'] ?? '');
  if (!eventId) return;
  const categories = await events.categoriesFor(eventId);
  const allDone = categories.every((c) => c.status === 'completed' || c.status === 'cancelled');
  if (allDone) await events.markCompleted(eventId); // emits event.completed → payout
},
```
Add a cron job `sweep-event-completion` that calls `markCompleted` for events with `status in (published, live)` and `endsAt < now - 24h`.

### 2. Cancelled events leave everyone "confirmed"

**What's wrong**
When a host cancels an event, or a draw is cancelled for too few players, we send the money back, but the player's registration stays `confirmed`. The system still treats them as playing.

**Example**
Event cancelled. Aman gets his ₹500 back. But the app still shows "You're in!", he still gets organizer messages, and he can still check in on the day.

**Fix**
Add `registration.refundForCancellation(registrationId)`, which moves `confirmed → refunded` (or `withdrawn` for free entries). Have the bulk refund call it for each entry, in the same step that queues the money refund.

**Code** (`src/modules/payments/service/index.ts`, inside `refundEach`)
```ts
for (const reg of confirmed) {
  await registration.markCancelledByOrganizer(reg.id); // confirmed → refunded/withdrawn
  await refundForRegistration({ registrationId: reg.id, reason, refundAmount: true, includePlatformFee: true });
}
```
Keep the order: notify first (it reads the `confirmed` list), then move the status.

### 3. A payment that finishes after the draw is cancelled is never refunded

**What's wrong**
When a draw is cancelled, we only refund **confirmed** players. Someone who was halfway through paying at that moment is skipped. If their payment completes a minute later, we confirm them into a cancelled draw and nobody refunds them.

**Example**
Registration closes at 6:00 pm and the draw is cancelled (only 3 of the 4 needed players). Neha opened the Razorpay screen at 5:59 and pays at 6:01. She's charged ₹500, shows as "confirmed", and the draw doesn't exist.

**Fix**
Two guards:
1. When a draw or event is cancelled, also expire every entry that is `payment_pending`, `payment_failed`, `waitlisted` or `awaiting_partner`, and release their seat holds.
2. In `confirmFromPayment`, refuse to confirm when the event or category is cancelled. It then throws `ILLEGAL_TRANSITION`, which the payment code already turns into a full automatic refund.

**Code** (`src/modules/registration/service/index.ts`, `confirmFromPayment`)
```ts
const category = await events.categoryById(row.eventCategoryId);
const event = await events.byId(row.eventId);
if (category.status === 'cancelled' || event.status === 'cancelled') {
  throw illegalTransition(status, 'confirmed'); // payments refunds it in full
}
```

**Added in the second pass:** the "is the draw still open?" check runs **before** the seat-hold transaction (`assertOpen`), so it can race with closing. The seat-hold query (`acquireHold`) only checks capacity. Add the status check to that SQL too, so a hold can never be taken in a closed or cancelled draw:
```sql
WITH locked AS (
  SELECT id, capacity FROM event_categories
   WHERE id = $1 AND status IN ('open', 'full')   -- new
   FOR UPDATE
), ...
```

### 4. Players can get a refund after the event is over

**What's wrong**
The cancellation cutoff is optional. If the host leaves it empty, the code treats it as "refund anytime", even after the draw is made or the event has finished. Cancelling also doesn't remove the player from the bracket.

**Example**
Karan loses in round 1 on Saturday. On Sunday he taps "Cancel registration" and gets his ₹500 back. The host loses that money, possibly after already being paid, so it becomes money the host owes us.

**Fix**
- Block cancelling when the category is `drawn`/`completed` or the event is `live`/`completed`.
- If no cutoff is set, use the event start time as the cutoff.

**Code** (`registration.cancel`)
```ts
const category = await events.categoryById(row.eventCategoryId);
if (['drawn', 'completed'].includes(category.status) || ['live', 'completed'].includes(event.status)) {
  throw new UserError('CANCELLATION_CLOSED', 'The draw is made — contact the organizer to withdraw.');
}
const cutoff = event.cancellationCutoffAt ?? event.startsAt;
const refundable = paidOnline && now() < cutoff;
```
Withdrawing after the draw should then go through the host, who marks a **walkover** in the bracket.

## Part B — Event creation

### 5. Paid categories can skip the "verified host" check

**What's wrong**
The "you need a verified payout account to charge money" check only runs when the event is first published. After that, a host can add a paid category, or change a free one to paid, without being checked.

**Example**
Sam has no bank account set up. He publishes a free event, then edits the category fee from ₹0 to ₹800. Players pay, and we have nobody to send the money to.

**Fix**
Move the check into a helper and call it from `publish`, from `addCategory` (when the event isn't a draft and the fee > 0), and from `updateCategory` (when the fee goes from 0 to above 0 on a published event).

**Code**
```ts
async function assertCanCharge(actor: Actor, eventStatus: string, feePaise: bigint) {
  if (eventStatus === 'draft' || feePaise === 0n || !deps.publishGate) return;
  const v = await deps.publishGate.canPublishPaid(actor.userId);
  if (!v.ok) throw new UserError(EventCode.ORGANIZER_NOT_VERIFIED, 'Paid draws need a verified payout account.');
}
```

**What's wrong**
A host can make the bracket while registration is still open, or even for a cancelled category.

**Example**
Registration is open until Friday. The host makes the draw on Wednesday with 12 players. Four more players pay on Thursday. They are "confirmed" but appear in no match.

In `generateDraw` / `regenerateDraw`, only allow it when the category status is `closed` (registration over) and the event isn't cancelled. To let a host start early, add an explicit "close registration now" button that runs the normal close step first.

```ts
if (category.status !== 'closed') {
  throw new UserError('REGISTRATION_STILL_OPEN', 'Close registration before making the draw.');
```

### 7. The host controls our platform fee and GST

**What's wrong**
`platformFeePaise` and `taxBps` are fields on the host's category form. Our fee and the tax rate are business and legal decisions, not the host's.

**Example**
A host sets platform fee = 0 and GST = 0%. We earn nothing and file the wrong tax.

**Correction from the second pass**
The app's host wizard never sends these two fields (`toCategoryInput` in `apps/player/src/features/host/model/submit.ts`). So today **every** paid category gets the server defaults: platform fee ₹0 and GST 18%. In practice PL4Y earns only the 10% host commission right now. The risk above needs someone calling the GraphQL API directly, so it's **Medium**, not High. It's still worth closing, and it's worth deciding whether the platform fee should really be ₹0 (see #36 for the GST question).

**Fix**
Remove both fields from `AddEventCategoryInput` and `UpdateEventCategoryInput`. Set them on the server from config (e.g. `PLATFORM_FEE_PAISE`, `ENTRY_TAX_BPS`), the same way `commissionBps` is already set.

**Code** (`addCategory`)
```ts
platformFeePaise: input.entryFeePaise > 0n ? config.PLATFORM_FEE_PAISE : 0n,
taxBps: config.ENTRY_TAX_BPS,
```

### 8. Category numbers aren't checked

**What's wrong**
Nothing checks that the numbers make sense. The worst case: the minimum number of players can be set **lower** than the bracket can handle.

**Example**
A host sets "minimum entries = 2" on a knockout draw. Registration closes with 3 paid players, so the draw is **not** cancelled. The host then tries to make the draw and gets "needs 4 entries". Three people have paid, there's no tournament, and nobody gets a refund.

**Second pass: the app allows this today.** The host wizard says a knockout needs only 2 players (`DRAW_MIN_ENTRIES.single_elim_with_plate = 2` in `apps/player/src/features/host/model/validate.ts`). The server needs 4. See #30.

**Fix**
Validate in `addCategory` and `updateCategory`:
- fee ≥ 0
- `capacity` ≥ the system minimum for the draw type (a knockout with capacity 3 can never be drawn)
- `minEntries` ≥ the system minimum for the draw type (4 knockout / 3 league / 6 groups)
- `minEntries` ≤ capacity
- `skillMin ≤ skillMax`, `ageMin ≤ ageMax`
- name not empty

Also add database `CHECK` constraints as a backstop.

**Code**
```ts
const floor = drawType === 'league' ? 3 : drawType === 'groups_knockout' ? 6 : 4;
if (input.entryFeePaise < 0n) throw invalid('Fee cannot be negative.');
if (minEntries < floor) throw invalid(`This draw type needs at least ${floor} entries.`);
if (minEntries > input.capacity) throw invalid('Minimum entries cannot exceed capacity.');
```
```sql
ALTER TABLE event_categories
  ADD CONSTRAINT event_categories_fee_check CHECK (entry_fee_paise >= 0 AND platform_fee_paise >= 0),
  ADD CONSTRAINT event_categories_tax_check CHECK (tax_bps BETWEEN 0 AND 10000),
  ADD CONSTRAINT event_categories_min_check CHECK (min_entries >= 1 AND min_entries <= capacity);
```

### 9. Extending the registration deadline doesn't move the close job

**What's wrong**
At publish we schedule a "close registration at time X" job. If the host later moves the deadline, the old job still fires at the old time.

**Example**
The deadline was Friday. On Wednesday the host extends it to Sunday to get more players. On Friday the old job closes registration anyway and cancels the draw for being under the minimum.

**Fix**
Inside `closeRegistration`, return early when `now < registrationClosesAt`. When `update()` changes the deadline, write an outbox row that reschedules the job.

**Code**
```ts
if (now() < row.registrationClosesAt) return { closed: [], cancelled: [] }; // deadline moved
```

### 10. Editing a published event skips the date checks

**What's wrong**
Publishing checks the dates make sense. Editing afterwards doesn't.

**Example**
After publishing, a host changes the end date to the day before the start date. Payouts are scheduled from the end date, so the money goes out too early.

**Fix**
After building the update, re-run the same date rules as publish on the merged result (start < end, deadline ≤ start, cutoff ≤ start). Check the location **before** saving anything, not after.

### 11. "Fixed once someone pays" ignores people mid-payment

**What's wrong**
Fee, size and dates lock only when someone is fully **confirmed**. A player who is on the payment screen doesn't count.

**Example**
Priya is on the Razorpay screen at ₹500. The host changes the fee to ₹700 at that moment. See #12 for what she gets charged.

**Fix**
Lock those fields when there are confirmed entries **or** live seat holds (`capacityOf(...).held > 0`).

Also lock `drawType`. Today it isn't in the locked list, so a host can turn a knockout into a league after everyone has paid for a knockout.

## Part C — Payments

### 12. The price charged can differ from the price shown

**What's wrong**
The registration saves the price the player agreed to. When creating the Razorpay order, the code ignores that saved price and works it out again from the category's **current** fee.

**Example**
Priya agreed to ₹500. The host changes it to ₹700. She taps Pay and Razorpay asks for ₹700.

**Fix**
Charge `registration.amountPaise`, the saved amount. If the current price differs, tell the player to start again; don't silently charge something else.

**Code** (`createOrder`)
```ts
const quote = await events.priceQuote(reg.eventCategoryId);
if (quote.totalPaise !== reg.amountPaise) {
  throw new UserError('PRICE_CHANGED', 'The price changed. Please register again.');
}
```
Once #11 is fixed, this should almost never happen.

### 13. Payment orders are created for entries that can't take one

**What's wrong**
`createOrder` only refuses already-paid entries. It lets an order be created for expired, withdrawn or waitlisted entries, doubles drafts with no partner yet, and cancelled events.

**Example**
Rahul's seat hold expired 10 minutes ago. He reopens the app, pays ₹500, and it's refunded automatically. He's confused, waits days for the refund, and we pay Razorpay's fee twice.

**Fix**
Only allow `payment_pending` or `payment_failed`, with a live seat hold, on an event that isn't cancelled.

**Code**
```ts
if (!['payment_pending', 'payment_failed'].includes(reg.status)) {
  throw new UserError('NOT_PAYABLE', 'This entry can’t be paid for. Please register again.');
}
```

### 14. Paying just after the hold expires can overfill a draw

**What's wrong**
When a seat hold has run out but the cleanup job hasn't run yet, a payment still confirms the player, even though that seat may already have been given to someone else.

**Example**
Draw of 16, one seat left. Arjun's 10-minute hold ends at 4:00:00. Meera takes the free seat at 4:00:05. Arjun's payment lands at 4:00:08 and he's also confirmed. That makes 17 players in a 16-player draw.

**Fix**
In `confirmFromPayment`, require a live hold for `payment_pending` too, not only for `payment_failed`. If there's none, throw. The existing late-payment code refunds the player in full.

**Code**
```ts
if ((status === 'payment_failed' || status === 'payment_pending') && !hold) {
  throw new SystemError(SharedCode.ILLEGAL_TRANSITION, 'Seat hold lapsed');
}
```
Make the hold a minute or two longer than Razorpay's checkout timeout, so honest payers don't hit this.

**⚠ Second pass: do #22 first.** Today a payment that arrives after the hold has run out is usually refunded anyway, because the release job has already marked the entry `expired`. If webhooks are late, that's already refunding honest payers (#22). Fix #22 (check on return, extend the hold while a payment is open), and only then tighten this check.

### 15. A failed refund is never retried

**What's wrong**
If Razorpay says a refund failed, we only write a log line. The refund keeps its Razorpay ID, so the "send refund" job skips it forever.

**Example**
Neha's refund fails because her bank rejected it. She's owed ₹500 and nothing will ever send it again.

**Fix**
On `refund.failed`: clear `gatewayRefundId`, increase an `attempts` counter, and queue `processRefund` again with backoff. Retry with a **new** idempotency key, because Razorpay would return the same failed refund for the old one. After 3 failures, mark it `failed` and alert staff (show it on the admin screen).

**Found in the second pass:**
- **A refund that was saved but never queued is never sent.** `refund()` saves the refund row, then queues the job in a separate step (`queue.processRefund(...).catch(log)`). If the server restarts between the two, or the queue insert fails, the row sits `pending` with no Razorpay ID. The reconciliation sweep only looks at refunds that already **have** a Razorpay ID (`gatewayRefundId: { not: null }`), so nothing ever picks it up. **Fix:** have the sweep also re-queue `pending` refunds with no Razorpay ID that are older than ~5 minutes, or write the queue job through the outbox in the same transaction.
- **A stuck refund freezes the host's whole payout.** The payout is held while *any* refund for the event is `pending` (`pendingRefundCount`). A refund stuck forever means the host waits forever. Once the retry above exists, also alert finance when a payout has been held for "refunds pending" for more than 3 days.

## Part D — Scoring

### 17. A player can make their own result final

**What's wrong**
Players on either side may score their own match live. Any live-scored result confirms **itself** after 15–60 minutes. The rule assumes a live score was entered by someone neutral, but a player can enter it.

**Example**
Vikram and his opponent finish a match. Vikram opens live scoring and taps points until he "wins" 21-5, 21-3. His opponent has gone home and doesn't see the notification. 30 minutes later the result is final, Vikram moves to the next round, and his rating goes up.

**Fix**
Only auto-confirm when the points were entered by **staff who are not playing**. A live score from a player counts as "typed": the opponent or the organizer has to confirm it.

**Code** (`src/modules/scoring/finality.ts`)
```ts
export function isAutoEligible(source: ResultSource, role: SubmitterRole): boolean {
  return role === 'staff'; // a player's own point log is not neutral
}
```
The submitter's role is already worked out correctly (staff who play count as `player`), so this one line closes the hole.

**Second pass: it's worse than it looks.** Nobody can be added as a scorer today (#26). So a "live" score is almost always typed in by one of the players, or by the host.

### 18. There's no way to correct a confirmed result

**What's wrong**
Once a result is confirmed, nobody can change it, not even the organizer. The docs plan this (R7/R8) but it's marked "not built".

**Example**
The scorer tapped the wrong side and the result auto-confirmed. The wrong player is now in the semi-final and both ratings are wrong.

**Fix**
Build `correctResult(actor, matchId, newResult)`:
1. Only an owner or manager may call it.
2. Lock the tournament.
3. If the **next** match hasn't started yet, undo the move: put the correct winner into the next match.
4. If the next match has already started, refuse with "next round already played — regenerate or void".
5. Write `result.corrected` to the outbox. The rating module undoes the old rating change and applies the new one.

All of this in one transaction.

---

### 19. Either side can undo points

**What's wrong**
Either player can undo points, including the final point after the result is submitted. That throws away the result and reopens the match.

**Example**
Losing 21-19 in the final, Dev keeps tapping undo on the last point. The match can never finish and his opponent's win is never submitted.

**Fix**
- During the match, only the person who entered a point (or staff) can undo it.
- After the result is submitted, only staff can reopen it. A player who disagrees uses **Dispute**, not Undo.

**Code** (`undo`)
```ts
if (reopening && !(who.role === 'owner' || who.role === 'manager' || who.role === 'scorer')) {
  throw new UserError('USE_DISPUTE', 'Dispute the result instead — the organizer will settle it.');
}
```

---

### 20. A dispute nobody settles blocks the tournament

**What's wrong**
A disputed result never confirms itself, and staff get one alert. If the organizer ignores it, the tournament never finishes, so (with #1) the host is never paid.

**Example**
A first-round dispute on Saturday morning. The organizer is busy and never opens the app. The bracket is stuck at round 2 all weekend.

**Fix**
- Remind staff again every 30 minutes while a dispute is open.
- After the event's end time + 24 h, escalate it to the PL4Y staff dashboard.
- Optionally, after 48 h, settle it with the submitted score as a "staff default", with a note.

---

### Also

- **Matches in cancelled events can still be scored.** In `assertCanScore`, refuse when the event is `cancelled`.
- **Players can play without checking in.** When starting a match, warn (or block, if the host turned check-in on) when a side isn't `checked_in`.

## Part F — Second pass: more gaps (21–36)

These came from reading the code paths the first pass skimmed: the seat-hold SQL, the Razorpay adapter and checkout pages, host payouts, partner invites, the GraphQL permissions, heats, and the app's host wizard. Each one has its own **How to verify** step.

### 21. A player who pays twice keeps paying twice

**What's wrong**
If the player taps Pay again more than **10 seconds** later, the app gets a **new** Razorpay order (`ORDER_REUSE_MS = 10_000`). If both orders end up paid, the second payment is quietly accepted: the entry is already confirmed, so nothing refunds it. The ledger records two charges for one entry, so the host is paid twice. If the event is later cancelled, only **one** of the two payments is refunded (`capturedPaymentFor` returns one payment).

**Example**
Riya taps Pay and picks UPI. A collect request goes to her UPI app, but she goes back to our app instead. 20 seconds later she taps Pay again and pays by card, and she's confirmed. A minute later she approves the old UPI request too, and ₹500 leaves her account again. Nothing refunds it.

**Fix**
1. In `applyCapture`, when the entry is already confirmed by a **different** payment, refund this one in full and alert finance.
2. Reuse the open order for as long as the seat hold lives, not 10 seconds.
3. Bulk refunds (#2) should refund **every** captured payment for a registration, not just the latest.

**Code** (`payments/service/index.ts`, end of `applyCapture`)
```ts
if (!confirmation.confirmedNow) {
  // Which payment confirmed the entry? Mark it when confirmedNow is true
  // (e.g. a `confirms_entry` flag on payments); every other capture is a duplicate.
  const keeper = await repo.entryPaymentFor(order.registrationId);
  if (keeper && keeper.id !== result.payment.id) {
    await refund(null, {
      paymentId: result.payment.id,
      amountPaise: result.payment.amountPaise,
      reason: 'duplicate_payment',
      idempotencyKey: `duplicate:${result.payment.id}`,
      registrationId: order.registrationId,
    });
    return;
  }
}
```

**Seen for real:** in the first test payment on 2026-10-03, the app created a second order (`order_TjQw8vp8izYox0`) for a registration already paid with `order_TjQsWvtI8DJAoy`, while the payment was still pending. That is this path.

**How to verify**
- *Test:* one registration, two orders, a capture webhook for each. Expect: one confirmation, the second payment refunded in full, and a payout quote that counts the entry fee once.
- *Manual (test mode):* open checkout, back out, wait 15 s, pay; then pay the first order from Razorpay's test page. The second payment should be refunded automatically.

### 22. A late webhook gets a paying player refunded instead of confirmed

**What's wrong**
A seat hold lasts **10 minutes** (`HOLD_TTL_MINUTES`). When it runs out, the release job marks the entry `expired`. Payments are confirmed **only** by the Razorpay webhook. If the webhook is late or lost, the backup check (`reconcilePending`) looks only at orders older than **30 minutes**. By then the entry is `expired`, so the "late capture" safety net **refunds** the player instead of confirming them.

The page Razorpay returns to after a successful payment (`/payments/razorpay/return`) verifies the signature, but doesn't check the payment. A player who pays slowly near the end of the 10 minutes (UPI can take a minute or two) hits the same thing.

**Example**
Razorpay's webhooks run 20 minutes late on a busy Saturday. Everyone who paid in that window sees "registration expired". 30 minutes later they're refunded, and their seats have gone to other people.

**Fix**
1. Add a `refreshPayment(registrationId)` mutation (captain only, rate-limited). It runs the same status check reconciliation uses (`settleOrderFromGateway`) for the open order, straight away. It asks Razorpay directly, so it's safe. The PayScreen already polls the registration every 3 seconds while checkout is open, so have the poll call this. Razorpay's test UPI flow ends on Razorpay's own "close this page" screen and **never reaches `/return`**, so the check can't rely on `/return` alone. Also run it on a verified `/return`.
2. When an order is created, extend the seat hold to e.g. 20 minutes from now (a new `registration.extendHold` port).
3. Run reconciliation after ~3 minutes instead of 30.

**Code** (payments service, sketch)
```ts
async function refreshPayment(actor: Actor, registrationId: string): Promise<void> {
  const reg = await registration.byId(registrationId);
  if (reg.captainUserId !== actor.userId) throw forbidden();
  const open = await repo.openOrderFor(registrationId);
  if (open) await settleOrderFromGateway(open.gatewayOrderId); // the only confirm path, as today
}
```

**How to verify**
- *Test:* the hold expires at minute 10 and the capture exists at minute 12 with no webhook. Call `refreshPayment`: the entry is **confirmed**, not refunded.
- *Manual:* temporarily point the Razorpay test webhook at a wrong URL and pay with `success@razorpay`. The entry should still confirm within a few seconds, through the app's 3-second poll.

### 23. A cancelled event can still pay the host

**What's wrong**
A cancelled event still gets a payout, worked out from the ledger like any other. Any payment that wasn't refunded counts as the host's money and goes to them 72 hours after the end date. Three ways to get there:
- a late payment confirmed after cancellation (#3);
- a duplicate payment (#21);
- a bulk refund that hit an error. Errors in `refundEach` are only logged, and the job still counts as a success, so it's never retried.

**Example**
An event is cancelled. One player's bulk refund fails on a database error, which is logged and skipped. Three days after the end date, the host receives that player's ₹450, and the player gets nothing back.

**Fix**
- In `automaticHold`, hold any payout for a **cancelled** event while a captured payment for that event isn't fully refunded (new reason `cancelled_event_unrefunded`), and alert finance.
- In `refundEach`, collect failures and **throw at the end**, so the job retries the failed ones. Successful refunds are idempotent, so retrying them is safe.

**Code**
```ts
// payouts.automaticHold
const ev = await conn.event.findUnique({ where: { id: payout.eventId }, select: { status: true } });
if (ev?.status === 'cancelled' && (await repo.unrefundedCaptures(payout.eventId, conn)) > 0) {
  return 'cancelled_event_unrefunded';
}
```
```ts
// payments.refundEach
const failed: string[] = [];
for (const reg of confirmed) { try { /* … */ } catch { failed.push(reg.id); } }
if (failed.length > 0) throw new Error(`bulk refund: ${failed.length} entries failed`); // job retries
```

**How to verify**
- *Test:* a cancelled event with one captured payment and no refund. `sendPayout` should end `held` with `cancelled_event_unrefunded`, and no transfer.
- *Test:* make one refund throw in `refundEach`. The job should fail and retry, and the other refunds should not be sent twice.

### 24. A suspended host can lift their own suspension

**What's wrong**
Finance can **suspend** a host's payout account, for example over fraud. But `savePayoutAccount` doesn't look at the current status: re-saving bank details sets the account back to `checking`, the automatic bank check passes, and it becomes `verified` again. The suspension is undone without any staff member deciding.

**Example**
Finance suspends Sam after complaints about a fake event. Sam re-enters the same bank details. A minute later his account is "verified" and his held payouts start going out.

**Fix**
Refuse to save while the account is `suspended`. Only `reinstatePayoutAccount` (admin/finance) can lift a suspension.

**Code** (`payouts.saveAccount`, before the upsert)
```ts
const current = await repo.accountByUser(actor.userId);
if (current?.status === 'suspended') {
  throw new UserError('PAYOUT_ACCOUNT_SUSPENDED', 'Your payout account is suspended. Please contact support.');
}
```

**How to verify**
- *Test:* suspend an account, then call `saveAccount`. Expect an error, the status still `suspended`, and no bank check queued.

### 25. Changing bank details can send a host's payouts somewhere else

**What's wrong**
Anyone signed in as the host can replace the bank account. The bank check compares the name the bank returns with the name typed **in the same form**, and the PAN is typed in the same form too. Someone who gets into a host's account can enter their own name, PAN and bank account and be auto-verified.

**Example**
Someone gets into Riya's email inbox, signs in to PL4Y, and saves their own bank details under their own name. The account verifies, and Riya's ₹16,000 payout goes to them.

**Fix** (when changing details that were already verified)
1. Ask for a fresh email OTP before saving.
2. If the new legal name differs from the previously verified one, send it to `needs_review` instead of auto-verifying.
3. Hold payouts for 48 hours after any bank change.
4. Email the account owner: "Your payout bank details were changed. Not you? Contact support."

**How to verify**
- *Test:* a verified account, saved again with a different legal name. Expect `needs_review`, not `verified`.
- *Test:* a payout due within 48 h of a bank change. Expect it `held`.

### 26. Nobody can be added to help run an event

**What's wrong**
Only the person who created the event has a role on it. There is no API or screen to add a co-host, a manager, a scorer or a check-in helper. `identity.addStaff` exists, but no mutation calls it, and nothing calls `syncOrganizerGrants`.

So the "neutral scorer" rules in scoring (R12: a scorer who watched may confirm at once) can never apply. Every live score comes from a player or the host, which is what makes #17 dangerous.

**Example**
An event with 8 courts and 64 matches. The host alone has to check everyone in, confirm every typed or disputed result, and answer every "organizer will settle it". If they lose signal for an hour, the whole event stalls.

**Fix**
Add `addEventStaff(eventId, email or userId, role)` and `removeEventStaff(eventId, userId)`. The owner can add managers and scorers, and managers can add scorers. Add a small "Team" section on the Manage Event screen.

**Code** (sketch of the mutation's core)
```ts
const actorGrant = await identity.grantsFor(actor.userId, eventId);
if (actorGrant?.role !== 'owner' && !(actorGrant?.role === 'manager' && role === 'scorer')) throw forbidden();
await identity.addStaff(eventId, targetUserId, role);
```

**How to verify**
- *Test:* the owner adds a scorer. The scorer can check players in and score, but can't edit the event, publish or see payouts. After removal, the scorer is refused on the very next request.

### 27. A doubles player can enter the same draw twice

**What's wrong**
The "already entered?" check when **starting** an entry (`start()`) only looks at entries you **captain** (`forCaptainInCategory`). If you're already someone's **partner** in the draw, you can still start your own team there.

```ts
if (await repo.playerHasLiveEntry(actor.userId, input.eventCategoryId, LIVE_STATUSES)) {
```

### 30. The app lets hosts create knockout draws that can never be drawn (#8, made worse)

**What's wrong**
The host wizard believes a knockout needs **2** players (`DRAW_MIN_ENTRIES.single_elim_with_plate = 2` in `apps/player/src/features/host/model/validate.ts`). The server needs **4** (`MIN_ENTRIES = 4` in `src/modules/tournament/draw.ts`). So the app accepts a knockout with capacity 2–3, or with minimum entries 2–3. The server checks neither (#8).

**Example**
A host creates a knockout with capacity 3. Three players pay. Registration closes, and 3 is not below the minimum of 3, so nothing is cancelled or refunded. "Generate draw" says it needs 4 entries. The draw can never happen, and the three players' money is stuck.

**Fix**
- **App:** set `single_elim_with_plate: 4`.
- **Server:** apply #8's checks.
- Better still, serve these minimums from the server (e.g. on the format or draw-type query), so the app and server can never disagree again.

**How to verify**
- *App test:* a knockout with capacity 3, or min entries 2, shows a validation error.
- *Server test:* `addEventCategory` with a knockout of capacity 3 is refused.

### 31. Finished events show at the top of Discover

**What's wrong**
Event search shows every `published` or `live` event, with **no date limit**, sorted by start date **oldest first**. The app doesn't send a date filter (`fetchDiscoverEvents`). Because of #1, finished events stay `published` forever, so old events pile up at the top of Discover.

**Example**
In December, the first cards in Discover are October tournaments that already happened.

**Fix**
When no `from` is given, show only events that haven't ended. Fix #1 as well, so finished events actually leave the `published` status.

**Code** (`events/repo/index.ts`, `searchIds`)
```ts
if (!filter.from) where.push(Prisma.sql`e.ends_at >= now()`);
```

**How to verify**
- *Test:* a published event that ended yesterday is missing from a default search, and a future one is present.

### 32. Heat-based sports never finish

**What's wrong**
For sports scored in **heats** (running, swimming, cycling, athletics, powerlifting, weightlifting, golf, bowling, archery and more), nothing ever marks the category `completed`. Only knockout and league draws do that. Heats can also be created while registration is still open (no status check in `createHeats`).

So the fix for #1 ("complete the event when every category is done") would leave **every event with a heat category open forever**, and those hosts would never be paid.

**Example**
A 5K run: the final heat closes on Sunday, but the category stays `closed`, the event never completes, and there's no payout.

**Fix**
- Add "Finish category" for heats (owner or manager, allowed once every heat is closed). It marks the category `completed` and writes the same outbox message tournaments use, so #1's completion check fires.
- Keep #1's time-based sweep as a backstop.
- Refuse `createHeats` until registration for the category has closed (as in #6).

**How to verify**
- *Test:* close the last heat, then call "Finish category". The category becomes `completed` and the event becomes `completed` (if every other category is done), which schedules the payout.
- *Test:* `createHeats` on an `open` category is refused.

### 33. Organizers and support can't fix a single entry

**What's wrong**
There are no tools to:

- refund one player, fully or partly;

The "offline" and "comp" payment types exist (`PaymentMode`), but nothing ever sets them. Support has no refund button at all.

- **Organizer:** `addOfflineEntry(categoryId, userId, mode: 'offline' | 'comp')`. It takes a seat through the same `acquireHold` path.

**How to verify**

## Part E — How to verify each fix

*Items 21–36 carry their own "How to verify" step above. This part covers items 1–20.*

For every fix, do two things:

1. **Automated test.** Write a vitest test that **fails before** the fix and **passes after** it. Put it next to the existing tests for that module and run `pnpm test`.
2. **Manual check.** Try it in the app or with GraphQL against a local backend, with Razorpay **test** keys. Run it with `pnpm dev:all` (API + worker); plain `pnpm dev` saves webhooks but never applies them. Pay with test UPI `success@razorpay` (or `failure@razorpay`). Card `4111…` is refused on this account ("domestic cards only"), so use an Indian test card if you need one.

Handy tools:
- **Database**: `npx prisma studio` to look at rows (registrations, refunds, payouts, ledger_entries).
- **Time**: the services take a `now()` dependency. In tests, pass a fake clock instead of waiting for hours.
- **Jobs**: in tests, call the job function directly (e.g. `events.closeRegistration(id)`, `scoring.sweep()`) instead of waiting for the worker.
